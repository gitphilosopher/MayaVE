# Changelog

All notable changes to MayaVE are documented here.

## [Unreleased]

### Features
- **VE11 Hybrid Semantic Router activated as runtime default** — `RouterConfig.backend` in `config/settings.py` now defaults to `"hybrid"`. `Processor._classify` routes commands through `CommandUnderstander` (`brain/router/understand.py`), producing a `CommandIR` (`READY`/`NEEDS_CLARIFICATION`/`UNKNOWN`/`REJECTED`) that bridges to `Router.dispatch` via `to_legacy_intent(ir)`. The legacy classifier (`IntentEngine`) remains available as a fallback backend. `HybridIntentEngine` (`brain/router/hybrid_engine.py`) is preserved as an unwired compatibility wrapper with shadow mode.
- **CUDA-accelerated Kokoro neural TTS** — Migrated virtual environment to official PyTorch CUDA build (`torch==2.14.0+cu126`). `TTSConfig.device` in `config/settings.py` now defaults to `"auto"`, resolving dynamically to CUDA when `torch.cuda.is_available()` is True and falling back cleanly to CPU otherwise. Verified concurrent execution on NVIDIA GeForce RTX 3050 Laptop GPU (4GB VRAM) coexisting with Ollama `llama3.2` without CUDA OOM, model eviction, or stability issues in tested workload.
- **Command IR router pipeline** — `brain/router/understand.py::CommandUnderstander` produces a `CommandIR` (`READY`/`NEEDS_CLARIFICATION`/`UNKNOWN`/`REJECTED`, `brain/router/ir.py`) through context rewrite (`context.py`) → guards → classifier confidence+margin gate → semantic retrieval (`semantic_router.py`, `command_vector_store.py`, separate SQLite file + fingerprint sidecar) → LLM fallback (`llm_fallback.py`, validated by `validate.py` against `config/command_domains.json`) → deterministic entity extraction (`entities.py`). A low-confidence command ends `UNKNOWN`, never a forced intent.
- **Router evaluation tooling** — `brain/router/eval_router.py` (retrieval sweeps, `--seed` for the command corpus), `eval_ir.py` (false-execution rate as primary metric, per-case output, `model_digest`), `failure_matrix.py` (cross-seed failure frequency), `diag.py`, and `datasets/router_eval/cases.jsonl` (60 cases); multi-seed run outputs are kept under `logs/runs60/`.
- **Candidate audit and staging tools** — `brain/dataset_tools.py` runs an automatic deterministic audit (malformed, duplicate, contradiction, overly generic, keyword/vocabulary confusability, `help`/`unknown` restoration checks, boundary phrases, templates, diversity; optional capped LLM judgment) after generation and via `candidates audit`; `datasets/stage_data.py` stages hand-written rows/cases with leak and near-duplicate checks (dry run by default); `datasets/review_candidates.py` writes a read-only review report; `candidates promote` now splits ≈80/10/10 per intent with cross-split dedup.
- **MayaNode event/memory producer + outbox sync (Step 3)** — `services/node/events.py::record_event()` and `services/node/memory_producer.py::record_memory()` are the only application-facing entry points for data bound for MayaNode: both validate locally (`services/node/protocol.py`), stamp a UTC timestamp and a unique `event_uid`, and queue into a new durable local outbox (`services/node/outbox.py`, `~/Maya/Node/outbox.json`, atomic `.tmp` + replace) rather than calling `/sync` directly. `NodeSyncManager._sync_once` now pulls up to `config.node.max_events_per_sync`/`max_memory_per_sync` pending items per round, pushes them alongside the cursor, and reconciles the outbox against the response — only items the server actually settled this round (any terminal event status; the exact `(key, updated_at)` pair sent for memory) are removed, so a batch cap, a mid-round crash, or Node staying offline never loses queued data; the cursor still only ever advances per the Step 2 contract. Adds the first real MayaVE event type, `mayave.turn_completed` (`{intent: string}`), registered identically on both sides; `protocol.ping` is unchanged. `config.node.enabled` still defaults to `False`, and recording events/memory never depends on the sync manager running or Node being reachable.
- **MayaNode inbound memory merge** — `NodeSyncManager._apply_incoming_changes` hands `changes["memory"]` to `ContextManager.apply_remote_memory_changes`, which accepts only `semantic_memory:*` keys, re-embeds locally, dedups against the existing store and inserts with `source="mayanode_sync"`; outgoing, `_sync_memory_to_node` mirrors only `user_stated` fact/preference memories (no embeddings, no compaction summaries). Incoming `changes["events"]` are intentionally not applied.
- **MayaNode versioned protocol layer** — `services/node/protocol.py` implements the contract in `docs/PROTOCOL_CONTRACT.md` (`protocol_version=1`, envelope validation, event-type registry, request builder, response version check, change-ordering check); `NodeClient.sync` validates outgoing events and the response (`SyncResult.from_response`) and adds `health()`.
- **MayaNode discovery + sync scaffolding** — `services/node/` (`discovery.py`, `client.py`, `identity.py`, `sync_state.py`, `sync_manager.py`) adds discovery (`GET /status` probed against a configured `base_url` then an ordered candidate list), connection (`POST /heartbeat`), and an empty-payload `POST /sync` loop that persists/advances a cursor (`~/Maya/Node/sync_state.json`, atomic `.tmp` + replace) and a stable `device_id` (`~/Maya/Node/device_id.txt`) across restarts. `NodeClient` is auth-ready (`Authorization: Bearer` header hook, unused by MayaNode today). `node_sync_manager` runs as a background task in `main.py`, backoff-guarded and never raising even when MayaNode is offline or `config.node.enabled=False` (default). Step 1 itself wired no application data through; Steps 3–4 above add it.
- **Shutdown and restart skill** — `skills/system/power.py` now handles the `shutdown`/`restart` intents (previously answered by the LLM, nothing happened) by asking "say yes to confirm"; `Router.dispatch` calls `resolve_pending` first so a one-shot request (30 s TTL) is confirmed, declined or dropped by the next utterance, and confirm runs `shutdown /s` or `/r /t 10` (no `/f`) in the executor.
- **Lock screen skill** — `lock_screen` intent routed to `skills/system/lock_screen.py` (`LockWorkStation` via ctypes; apology on non-Windows), immediate by design with no confirmation because it is reversible.
- **Spoken timer reminder text** — `timer._extract_reminder` captures "remind me to X" (duration stripped, max 120 chars) and the alert speaks "Time's up, senpai! Reminder: X."

### Improvements
- **Configurable adaptive worker runtime, session persistence & resume controls** — Enhanced the unattended maintenance coordinator runtime (`.maya/maintenance/adaptive.py`, `.maya/maintenance/coordinator.py`, `.maya/maintenance/terminal_approval.py`) to support operator-selected session durations with monotonic in-process deadline enforcement and cross-restart resumption:
  - *Configurable session runtime*: Supported operator-selected durations (e.g. 1800s, 3600s, 7200s, 14400s, 21600s) via `AdaptiveConfig.hard_timeout_sec` and coordinator CLI flags (`--hard-timeout`/`--timeout-seconds`). Standardized default session duration to 6 hours (21600.0s) with a strict 24-hour upper bound (86400.0s).
  - *Input validation & rejection*: Enforced strict validation rejecting negative, zero, non-finite (`NaN`, `Inf`, `-Inf`), or excessive (>86400.0s) durations in both CLI parsing and `AdaptiveConfig.__post_init__`.
  - *Monotonic in-process deadline*: Enforced monotonic deadline checks (`time.monotonic()`) before and after each scheduling step to eliminate wall-clock drift, NTP adjustments, or system clock alterations during unattended runs.
  - *Session state persistence & resumption*: Persisted structured session state (`.maya/maintenance/active_session.json`) recording session ID, status (`RUNNING`, `INTERRUPTED`, `EXPIRED`, `COMPLETED`, `MANUAL_STOP`), requested duration, ISO start/deadline timestamps, and halt reason. Added `--resume` and `--new-session` CLI options. Resuming an active session preserves the original persisted deadline timestamp without resetting or inflating the operator's time budget; resuming an already-expired session halts immediately with zero tasks dispatched.
  - *Session summary metrics*: Updated session reporting in markdown and JSON (`generate_session_summary`) to include requested duration, formatted session start/deadline timestamps, remaining budget, and specific halt attribution.
  Covered by 10 focused regression tests in `.maya/tests/maintenance/test_adaptive_scheduler.py` (31 adaptive tests total).
- **Adaptive worker six-hour runtime limit, safe manual interrupt & retry elevation** — Enhanced the unattended maintenance worker loop (`.maya/maintenance/adaptive.py`, `.maya/maintenance/coordinator.py`, `.maya/maintenance/models.py`) to enforce six-hour operational boundaries and clean manual shutdown:
  - *Six-hour default runtime limit*: Configured `AdaptiveConfig.hard_timeout_sec` and coordinator CLI `--hard-timeout` to default to `21600.0` seconds (6 hours), preventing runaway unattended sessions while preserving override capability.
  - *Graceful manual stop & session report generation*: Wrapped `AdaptiveWorkerScheduler.run_until_idle()` in clean `KeyboardInterrupt` handling to stop new task scheduling, safely join active worker threads with bounded timeout, accurately calculate session elapsed duration, and persist the morning review summary (`session-<id>.json` and `.md`).
  - *Task retry elevation*: Hardened `TaskDefinition.from_dict()` to guarantee `max_attempts >= 3` (1 initial attempt + 2 retries), ensuring legacy serialized task records with `max_attempts: 2` receive full retry capacity without starving failure recovery.
  Covered by 4 focused unit tests in `.maya/tests/maintenance/test_adaptive_scheduler.py` (21 adaptive tests total).
- **Adaptive worker safety relaxation, configurable hard timeout & preflight integrity validation** — Updated overnight worker safety boundaries (`.maya/maintenance/adaptive.py`, `.maya/maintenance/scheduler.py`, `.maya/maintenance/models.py`, `.maya/maintenance/coordinator.py`) to align with unattended overnight maintenance requirements:
  - *Unbounded session execution & configurable hard timeout*: Removed the arbitrary 2-task session cap, allowing unattended sessions to process all eligible queue tasks until manual stop, empty queue, or a configurable hard timeout (`--hard-timeout`/`--timeout-seconds`).
  - *Recoverable task retry limits*: Increased default `max_attempts` from 2 to 3 in `TaskDefinition` (`models.py`), permitting an initial attempt plus at most two retries per task.
  - *Independent task continuation & failure isolation*: Tasks with remaining attempts (`attempts < max_attempts`) are treated as recoverable; `DependencyScheduler` prioritizes unattempted fresh tasks ahead of retries (`t.attempts` ordering), preventing failure retry loops from starving independent tasks.
  - *Operational pause on permission blocks*: Tasks entering `NEEDS_APPROVAL` are paused without halting the scheduler loop, releasing their worker slot once child processes confirm termination and allowing independent eligible tasks to continue.
  - *Preflight integrity validation*: Implemented `validate_preflight_integrity()` verifying ledger coherence, checkpoint consistency, worktree paths, and Git branch ownership before launching unattended execution.
  - *Strict risk boundaries*: Re-affirmed strict exclusion of `HIGH` and `VERY_HIGH` risk tasks from unattended execution.
  - *Focused regression tests*: Added targeted tests in `.maya/tests/maintenance/test_overnight_safety_gates.py`, verified across the full 130-test maintenance test suite.
- **Overnight worker safety gates, risk gating, and persistent terminal approval** — Implemented comprehensive unattended execution boundaries, risk-tier gating, unintegrated prerequisite code isolation, hard run-batch limits, and durable interactive terminal approval for the MayaVE maintenance coordinator (`.maya/maintenance/scheduler.py`, `.maya/maintenance/adaptive.py`, `.maya/maintenance/coordinator.py`, `.maya/maintenance/terminal_approval.py`).
  - *Risk-tier gating & ordering*: `DependencyScheduler` and `AdaptiveWorkerScheduler` enforce strict risk boundaries via `--max-risk` (`choices=["LOW", "MEDIUM"]`, default `MEDIUM`). `HIGH` and `VERY HIGH` tasks are strictly excluded from unattended scheduling and held for interactive operator authorization. Scheduling prioritizes `LOW`-risk tasks ahead of `MEDIUM`-risk tasks, and within each tier prefers tasks that unblock more downstream dependents (`-downstream_counts`), with deterministic task ID tie-breaking.
  - *Hard run cap & sequential execution*: Enforced `--max-tasks` with default 2 and hard cap at 2 for unattended pilot execution. Rejects invalid task caps (< 1 or > 2) in both CLI parsing and `AdaptiveConfig` validation. Enforced sequential single-worker execution (`initial_concurrency=1`, `max_concurrency=1`).
  - *Stop-on-failure safety*: Enforced `--stop-on-failure` (default True in coordinator CLI) halting subsequent worker spawning upon any task failure, quality-gate rejection, unexpected worker exception, or permission denial.
  - *Unintegrated prerequisite code isolation & file overlap checks*: `DependencyScheduler` detects when a candidate task targets files overlapping with an unintegrated verified task (such as `T1-01` residing in its isolated worktree without integration into `main`), or when a downstream task depends on an unintegrated verified task whose code is absent from the repository baseline `HEAD`. Holds candidate tasks with actionable error messages requiring explicit baseline integration.
  - *Preserved unexpected-worktree protections*: `WorktreeManager.reconcile_all` preserves `NEEDS_APPROVAL` safety blockers for tasks with unmanaged pre-existing workspaces (`T1-02` through `T1-05`, `T4-03`), preventing accidental overwriting or adoption without operator authorization.
  - *Persistent terminal approval manager*: Introduced `TerminalApprovalManager` (`.maya/maintenance/terminal_approval.py`, `.maya/maintenance/approvals.json`) providing durable permission request tracking with interactive terminal decisions (`[A]pprove`, `[D]eny`, `[I]nspect`, `[S]kip`, `[E]xit`). Approvals strictly validate the exact reviewed operation, target, and scope, ensuring any broadened or modified scope requires fresh operator review. Added coordinator CLI commands `--terminal-approval`, `--list-approvals`, `--approve-request`, `--deny-request`, and `--inspect-request`.
  - *Per-task & session reporting*: Automated saving per-task execution markdown reports (`.maya/reports/task-<task_id>-<timestamp>.md`) and durable session summary reports (`.maya/reports/session-<session_id>.json`, `.maya/reports/session-<session_id>.md`).
  Covered by 14 focused regression tests in `.maya/tests/maintenance/test_overnight_safety_gates.py` and `.maya/tests/maintenance/test_persistent_terminal_approval.py`, and verified across the complete 127-test maintenance suite.

- **VE11 Optimization 31: Ollama GPU Residency & VRAM Budget Optimization** — On the target RTX 3050 Windows runtime, resolved concurrent GPU/VRAM contention between Ollama `llama3.2` and GPU Kokoro TTS by configuring `num_ctx = 2048` as default in `config/settings.py` and forwarding request options across `services/llm/llm_service.py`, `main.py`, and `brain/router/llm_fallback.py`.

- **VE11 Optimization 30: Live Runtime Ollama GPU Contention & VRAM Attribution Audit** — Comprehensive attribution audit isolated the dual root causes behind live runtime performance degradation on Windows 11.
  - Confirmed Ollama TTFT ~2.1s root cause: Windows 11 IPv6 loopback connection attempt on `localhost` timed out after exactly 2,012.99 ms before falling back to IPv4 `127.0.0.1:11434`. Addressed by standardizing `base_url` to direct IPv4 `http://127.0.0.1:11434`.
  - Confirmed Kokoro >15s timeout root cause: High VRAM pressure near the 4GB ceiling forced Ollama into mixed 78% GPU / 22% CPU layer placement, saturating PCIe bus bandwidth and triggering WDDM CUDA execution dilation during concurrent Kokoro synthesis.
  - Confirmed BGE isolation: In-process local BGE verified consuming 0.0 MB VRAM on CPU and completing >350 ms before Ollama/Kokoro overlap.
- **VE11 Optimization 28: Kokoro Timeout Fault-Containment & Recovery** — Resolved the critical asyncio event-loop freeze defect discovered during OPT27 where synthesis timeouts synchronously blocked on `_kokoro_lock`.
  - Bounded non-blocking recovery contract implemented: When `asyncio.wait_for` times out in `_run_kokoro()`, the worker is marked as stale (`_kokoro_stale_worker.set()`) and `None` is returned immediately to the caller without acquiring `_kokoro_lock` on the asyncio event loop thread.
  - Event-loop lag during timeout reduced from **~98,925 ms freeze to 85.93 ms (99.9% reduction)**, completely preventing WebSocket ping/pong starvation and avatar renderer disconnections.
  - Stale worker containment: Any incoming synthesis request while a stale worker remains active inside native CUDA execution is rejected immediately (**0.06 ms**), preventing concurrent forward passes, shared KPipeline corruption, race conditions, or CUDA OOM.
  - Deferred pipeline reset: When the stale worker terminates its native call and releases `_kokoro_lock`, its `finally` block executes `_do_reset_pipeline()` off the event loop, safely resetting the shared pipeline singleton and restoring full synthesis availability.
  - Zero normal-path overhead: GPU synthesis alone verified at median **192.30 ms**; concurrent sentence streaming verified at median TTFA of **1,293.56 ms** with 100% success (20/20).
- **VE11 Optimization 27: Kokoro Execution Isolation Audit** — Comprehensive 5-mode empirical benchmark (100 total turns across Mode A: GPU Kokoro alone, Mode B: Ollama alone, Mode C: GPU Kokoro + Ollama concurrent, Mode D: CPU Kokoro + Ollama concurrent, and Mode E: Sequential GPU scheduling) completed; no production change justified.
  - Concurrent GPU Kokoro + Ollama streaming (Mode C) verified 100% reliable (0/20 timeouts) with median phrase synthesis duration of **255.66 ms** (p95 **379.73 ms**) and median conversational TTFA of **1,149.15 ms** (p95 **1,271.76 ms**).
  - CPU execution isolation (Mode D) firmly rejected: Kokoro synthesis duration degraded to median **1,970.87 ms** (+670.9%) and conversational TTFA inflated to median **2,873.97 ms** (+150.1%, p95 4,210.22 ms), severely violating interactive voice pacing.
  - Sequential GPU scheduling (Mode E) firmly rejected: Waiting for Ollama turn completion before GPU synthesis inflated conversational TTFA to median **2,030.56 ms** (+76.7%, +881.41 ms penalty), destroying sentence-level streaming pipelining.
  - Forensic root cause attributed: The intermittent 15.0s timeout in `maya.log` was an isolated startup transient caused by in-process model retraining memory pressure and WDDM paging, compounded by a timeout handler lock stall on `_kokoro_lock`. Standard sentence-pipelined GPU concurrency remains optimal.

### Architecture
- **Merged intents** — `open_app`/`open_website` → `open_target`, `note_create`/`note_append` → `note_write`, `note_read`/`note_list`/`note_open` → `note_view`, `set_reminder` → `set_timer`; skills decide the sub-operation from wording and `dataset_tools migrate-legacy-intents` relabels retired ids across splits and candidates. `help` and `unknown` are live intents again (see `docs/CONTRIBUTING.md`).
- **Config-driven command registry** — `config/command_domains.json` (25 `domain.operation` entries with entities, `target_mode`, `requires_confirmation`, semantic seeds) is a projection of the skill-mode intents in `datasets/intents.json`; `CommandRegistry`/`load_specs` validate it at load and reject a seed shared by two operations; the vector corpus is fingerprinted against it and a stale corpus only warns.
- **Command-level retrieval** — semantic scoring collapses per-seed vectors to one score per `domain.operation` before the top-k cut; margin is best minus second-best distinct command (`schemas.aggregate_by_command`).
- **Listening state broadcast** — `main.on_speech` broadcasts `state:listening` only when Maya is not PROCESSING/SPEAKING, empty STT resets to IDLE with baseline behavior, and the FSM no longer overwrites an in-flight turn, giving the sequence `listening → processing → speaking → idle`.
- **WebSocket last-state replay** — `ws_server` records `_last_state` on every `broadcast_state` (even with no clients, default `idle`) and `_handler` sends it to each new client, so the frontend's `_currentBackendState` is set at connect instead of staying `null` until the first broadcast.
- **Barge-in during processing and filler** — `state.can_interrupt()` allows PROCESSING with a live registered speech task, `on_speech` snapshots it instead of `is_speaking()`, and `query()` re-sets `_filler_done` in a `finally` so a cancelled filler never blocks the first phrase.
- **Timer alert routing** — the alert speaks through the `Speaker` injected by `Router` under `run_interruptible`, is queued on the command worker via `queue_manager.put_job` so it runs in order with commands, and the expired timer is removed from `_timers` before the alert.
- **Unreferenced background tasks** — `main.py` keeps `ws_task` with `_on_ws_done` failure logging and `ContextManager` keeps `_bg_tasks`.
- **Duplicate elongation helper removed** — `llm_service.py` keeps only the non-recursive `_elongation_re_sub` definition.
- **Sleep phrase matching centralised** — sleep-command detection moves from a `main.py` substring set to `core.wake_word.is_sleep_command`, next to the wake/barge-in matcher (importable without pulling in Kokoro); `main.on_speech` calls it instead of `_SLEEP_TRIGGERS`.
- **Shared spoken confirmation matcher** — `core/confirmation.py` (`is_confirm`/`is_deny`, whole-utterance yes/no phrases) is used by `power.py` and `notepad.py`; each skill still owns its own one-shot pending request and TTL, and `Router.dispatch` calls both resolvers before intent routing.
- **Frontend arbitration layers** — `expression-controller.js` (per-key layers `BASE<EMOTION<ACTION<LIPSYNC<BLINK`), `animation-controller.js` (bone ownership `BASE<FIDGET<ACTION` with a 350 ms handoff), `life-motion-controller.js` (breathing/posture/shoulders/hips at BASE tier) and `gaze-controller.js` (attention session, boredom ramp, eye/head offsets) are shared singletons driven from `main.js`'s single frame loop.

### Issues

The previously cited `diag_llm_seed*.txt` files are absent; verify actual model outputs before changing this fail-closed behavior.
- **Power confirmation and countdown** — [Potential] Confirmation is one-shot and accepts a bare confirmation phrase; a 10-second OS shutdown/restart countdown has no voice abort. No unintended power action is demonstrated; decide whether cancellation during the countdown is a product requirement before changing the flow.
- **Wake window boundary** — [Potential; static behavior] Wake recognition uses fixed, non-overlapping two-second windows, so a phrase split across windows may be missed. Runtime frequency has not been established.
- **Sparse classifier classes** — [Validation pending] In the current data snapshot, 28 of 41 intents are below their `min_examples` target. The cited recall/accuracy metrics are stale, and `datasets/training/candidates.jsonl` is currently empty; measure current per-class performance before changing training data.
- **Skill dispatch interruption gap** — [Limitation] Skill work before its first speech call is not registered as an interruptible task; a barge-in or sleep request may not cancel in-flight pre-speech work.
- **Critical-path latency** — [Potential; current impact unmeasured] Semantic-memory embedding can precede the first LLM token when memories exist, and streamed speech waits for per-phrase playback completion. Existing timing instrumentation can be used to establish impact before optimization.

- **Recent conversation window is not persisted** — [Limitation] The 50-entry recent history is in-memory and is lost on restart; durable semantic memory follows a narrower write policy.
